## TL;DR

Planet generation flips from noise-first (V1–V3: hard to control, mushy coastlines, no guaranteed flat land) to structure-first: a spherical Voronoi **cell graph** where continents, mountain ridges, biomes, and rivers are decided as discrete per-cell/per-edge properties, and noise is demoted to small surface detail. Rendering is deliberately an open question — CDLOD is *not* assumed; a cell-native adaptive mesh is the leading candidate because the authored structure lives on the graph, not in a heightfield. Everything is built and tested in isolation (pure sublibrary + dedicated lab page) before any integration.

## Why (V1–V3 post-mortem, condensed)

Four iterations of global 3D noise (fractal baseline → signed continents → domain warping + biome masks → calibrated masks + live sliders) all fought the same root cause: with noise, every gameplay requirement is an *emergent hope*, not a guarantee. Specifically:

- Mountain ridges never form connected walls that block ground movement.
- Coastlines are isolines through a continuous field — never crisp.
- "Flat buildable meadows" require masking hacks that then flatten the mountains too.
- Control knobs are noise frequencies/amplitudes, which don't map to gameplay intent.

## Goals

Unique, fun, controllable planets for physics gameplay (flying/driving vessels, base building):

1. **Mountain ridges as movement blockers** — connected ridge cells, guaranteed by construction (plate boundaries), not by noise luck.
2. **Clear continents & crisp shorelines** — land/water is a per-cell boolean; the coastline is a polyline of cell edges.
3. **Discrete biomes** — climate-driven (desert, tundra/ice caps, jungle/rainforest, taiga, savanna) plus relief-driven (meadow, hills, canyon, mesa, alpine, dunes) as *cell tags* with enforced properties (meadow ⇒ flat ⇒ buildable).
4. **Rivers that always reach the sea** — downhill walks along cell edges.
5. **Planetary scale, shape-agnostic** — sphere first; the same graph algorithms run on a flat/infinite 2D lattice later.
6. **Meaningful knobs** — "plate count", "ridge height", "sea level %", "cell density" instead of octaves and lacunarity.
7. **Deterministic & seed-driven** — same seed ⇒ same planet, pure functions, unit-testable without Three.js.

Deliberately irregular cells (relaxed Voronoi, per Amit Patel's *Polygonal Map Generation*), **not** a hex grid — irregularity hides the tiling, avoids the icosahedron's 12 pentagons, and gives more variety.

## Architecture

### Layer 1 — Cell graph (pure, framework-free)

```
(seed, params) → PlanetGraph {
  cells,       // spherical Voronoi cells: center, polygon corners, neighbor ids
  edges,       // shared boundaries with left/right cell ids
  plates,      // plate id per cell, plate motion vectors
  elevation,   // per-cell (+ per-corner interpolated) elevation
  water,       // per-cell boolean + lake detection
  biomes,      // per-cell biome tag
  rivers,      // edge chains from source cells to coast
  coastlines,  // extracted closed polylines of land/water edges
}
```

Pipeline stages (each pure, independently testable):

1. **Point distribution** — Fibonacci spiral on the sphere → N seed points (params: cell count, optionally density variation later).
2. **Lloyd relaxation** — k iterations of move-to-centroid + reproject, to turn clumpy into nicely irregular.
3. **Spherical Voronoi** — 3D convex hull of the points *is* the Delaunay triangulation; Voronoi cells are its dual (corners = triangle circumcenters projected to sphere). No spherical-geometry special cases.
4. **Plates** — seed P plates, flood-fill cells, assign each plate a random motion vector. Edge classification: convergent / divergent / transform from relative motion.
5. **Land/water** — plate type (continental/oceanic) + a low-frequency perturbation ⇒ per-cell boolean, targeting a sea-level % param. Small islands/lakes emerge from the perturbation.
6. **Elevation** — combined from: convergent boundary uplift (ridge cells, decaying with graph distance from the boundary), BFS distance-from-coast for continent interior swell, and per-biome amplitude. Elevation is authored per cell, with corner values blended from adjacent cells so slopes are controllable.
7. **Climate** — two derived per-cell scalars, computed before biome rules:
   - **Temperature** — from latitude (pole-to-equator falloff) minus elevation lapse (higher = colder). Poles get ice caps *by construction*, not by noise luck.
   - **Moisture** — BFS distance-from-ocean/river (closer = wetter), optionally biased by a simple prevailing-wind direction per plate/latitude band (windward coasts wetter, leeward interiors drier — enough to justify deserts forming in continental interiors/rain-shadows without a full atmospheric sim).
8. **Biomes** — a Whittaker-style lookup over (temperature, moisture, elevation, slope), Red-Blob-Games style:

   | | dry | medium | wet |
   |---|---|---|---|
   | **cold** (poles/high alpine) | tundra | taiga/snow | glacier/ice cap |
   | **temperate** | steppe/dunes | meadow / hills | jungle/temperate forest |
   | **hot** (equatorial) | desert | savanna | rainforest/jungle |

   Plus elevation/slope overrides independent of climate: **alpine** (high elevation, any climate), **canyon** (high slope + low moisture history), **mesa** (stepped elevation + dry). Each biome carries its *detail recipe* (noise amplitude/character used only within that cell, e.g. meadow ≈ 0, dunes = rolling low-frequency, canyon = carved steps). Ice-cap cells at the poles are also flagged as water-equivalent for rendering (frozen ocean) vs. land ice (glacier) so shorelines stay meaningful near poles.
9. **Rivers** — pick high-moisture/high-elevation source cells, walk strictly downhill along cell corners/edges to the sea; widen by accumulated flow; carve elevation along the path; contribute back into the moisture pass (river-adjacent cells get a moisture bonus, which is what lets jungle hug a river through an otherwise drier belt).
10. **Coastline extraction** — walk land/water edges into closed polylines (needed for crisp-shore rendering and shoreline gameplay queries).

### Layer 2 — Rendering (reshaped 2026-08-26 — chunked cell-native mesh, NOT CDLOD)

CDLOD (runbook 019) was painful, is in an unfinished state, and was designed for continuous heightfields. V4's source data is a polygonal graph, which suits a different architecture. Three lessons from the V1–V3 and CDLOD attempts drive this shape directly:

- **Draw calls were the actual killer before**, not triangle count — so the unit of rendering is a **chunk** (a merged run of ~100–ish cells baked into one `BufferGeometry`), never one draw call per cell.
- **Camera and physics are decoupled** — you can orbit to see the whole planet while a vessel sits on the surface, so the visual mesh's LOD and the collider's resolution must be free to differ completely. They should never be forced into "one mesh serves both."
- **Terrain is going to be edited at runtime** (base-building flatten/dig), so the height source can't be a one-shot bake — it has to be a live function that both edits and rebuilds can call at any time.

The bridge across all three is a single **canonical elevation function**, `sampleElevation(pointOnSphere) → height`: pure, deterministic, derived from the cell graph (barycentric blend of the 3 corner elevations of whichever cell the point falls in), plus — once base building lands — a sparse **override layer** (player edits stored as save data, checked before the graph value). Everything else reads from this one function instead of agreeing with each other by convention:

- **Visual chunks** displace their vertices by sampling it at whatever density their current LOD level calls for.
- **Colliders** are small, high-resolution mesh patches sampled from the same function, generated only near vessels/the player — independent of what the camera or visual LOD is doing.
- **Terrain edits** (flatten a pad) write into the override layer, then trigger a rebuild of only the affected chunk(s) and any nearby collider patches — nothing else on the planet touches disk or GPU.

LOD is **per-chunk, discrete** (2–4 fixed subdivision levels picked by camera distance to the chunk), not per-cell adaptive scoring. Border stitching only has to agree between whichever two discrete levels are adjacent, not an arbitrary continuum — far simpler than full crack-free adaptive stitching. Per-cell adaptive LOD (view-angle/horizon-weighted scoring, biome-importance budgets) is **deferred**, not abandoned: the chunk architecture doesn't block adding it later if large/medium planets or close orbital flythroughs need it, but it is not built until a real case proves it's needed. Coastline and ridge cell edges stay real mesh geometry either way (crisp by construction — no shader/depth-fade shoreline), because chunks are still built by tessellating the graph, not by rasterizing it into a heightfield.

Water rendering: separate ocean sphere mesh clipped to ocean cells, meeting the coastline polyline exactly; optional signed-distance-to-coast attribute for shore foam/shallows shading.

Because planet size is a player-facing choice (small/medium/large), the architecture must hold up across the whole range even though the near-term focus is small planets — chunking + discrete per-chunk LOD is what makes that scale, not a small-planet-only shortcut.

Exit criteria (rescoped 2026-08-26): not a single fps floor. Measure **frame time in ms for this subsystem alone** (chunk render + any active collider rebuilds) on a rotating small planet, at ground level, low grazing angle, and orbit — crisp coastline, one sharp ridge range, flat meadows, no cracks between chunk LOD levels, no visible seam between a chunk's visual mesh and its collider patch. The ms budget should leave clear headroom for everything else the game will run in the same frame (physics, other rendering, gameplay logic) — a global "60fps" number was never the real target, just a conservative sanity floor.

### Layer 3 — Physics & gameplay hooks (later, but shapes decisions now)

- Ground colliders (Jolt static mesh, streamed by proximity to vessels) are sampled from the *same* `sampleElevation()` function as the visual chunks, not literally the same mesh — see Layer 2. This is what lets the camera orbit out to see the whole planet while a vessel's collider stays high-resolution locally.
- Gameplay queries answered from the graph, not the mesh: `biomeAt(dir)`, `isBuildable(cell)`, `distanceToCoast(cell)`, `ridgeBetween(cellA, cellB)`.

## Isolation & placement

- Lives as a new pure sublibrary (working name `triangular-engine/worldgen` — **name TBD**) with its own `public-api.ts`, mirroring `scatter`/`terrain`/`procedural` conventions: deterministic core, no Angular/Three coupling, adapters at the edge.
- **No integration** with `triangular-engine/terrain` (CDLOD), `celestial` surfaces, or BSP until the POC proves out. No changes to existing planet code.
- Dedicated demo-app lab page (e.g. `/cell-planet-lab`) with live regeneration: seed, cell count, plate count, sea level, ridge height, relaxation iterations.
- 2D debug views matter as much as 3D: flat map projections of plates / elevation / biomes / rivers (Amit-style) are the fastest way to judge generation quality without touching rendering.

- **M2.5 — Real lake water bodies + river flow accumulation — done (2026-08-26)**: prompted by comparing this system against Amit Patel's [Polygonal Map Generation for Games](http://www-cs-students.stanford.edu/~amitp/game-programming/polygon-map-generation/) — see that write-up for the source technique on both items below.
  - **Water bodies**: `water-bodies.ts` (`classifyWaterBodies()`) flood-fills `tectonics.isLand`'s water cells into connected components; the single largest component is `'ocean'`, every other component is `'lake'`. Before this, `isLand` had no notion of connectivity — a landlocked water pocket and the open ocean were both just "not land", and the only `'lake'`-adjacent concept was `rivers.ts`'s `lakeCorners` (river-termination local minima, not an actual water-body classification). `computeBiomes()` now takes `waterBodyKind` and emits a distinct `'lake'` biome (frozen water of either kind still reports `'ice_cap'`, unchanged); moisture's ocean-seeded BFS already treated all `!isLand` cells as sources so it needed no change. This is a pure classification pass over existing water, not depression-filling — it won't create a new lake by filling an interior elevation minimum that sits above sea level (a separate feature, not done here). 3/3 new unit tests passing (`water-bodies.spec.ts`): every water cell gets classified and adjacent water cells always share a kind (connectivity invariant), a hand-flipped single land-locked cell classifies as `'lake'` while a real ocean cell exists elsewhere, and an all-land graph returns all-null. `/cell-planet-lab`'s biome color mode and 3D preview now render lakes in a distinct blue from ocean.
  - **River flow accumulation**: `traceRivers()` now tracks a running per-corner visit count as each source's downhill walk proceeds. Downhill stepping is a pure function of the current corner (always the single lowest neighbor), so once two sources' paths converge on a corner they are identical from there on — counting visits per corner is therefore exactly the discharge at that corner, no separate merge-detection needed. Traced in two passes (find every path's corner indices and finalize the counts, then read the counts back per path) so a source visited later in iteration order can't leave an earlier path's recorded flow stale. `IPlanetRivers.riverFlow: number[][]` is a new field parallel to `riverPaths`; `riverPaths` itself is unchanged so the M2/M3 river tests needed no changes. The `/cell-planet-lab` 2D unwrap's rivers-mode overlay now strokes each river segment at `baseWidth * (1 + 0.5·sqrt(flow−1))`, so merged rivers visibly widen downstream (canvas 2D supports per-segment `lineWidth` cheaply). The 3D preview's river overlay is still a uniform-width `LineSegments` — `LineBasicMaterial`'s `linewidth` is ignored by most WebGL backends, so matching this in 3D needs three.js's fat-line addon (`Line2`/`LineMaterial`) or a width-varying ribbon mesh; **deferred**, not done here. 1 new unit test passing (`rivers.spec.ts`): flow is ≥1 everywhere and never decreases going downstream along any single path, exercised with a raised `sourceCount` to guarantee at least one actual merge.
  - **Considered and explicitly not taken from the article**: *noisy edges* (jittering polygon/coastline/river boundaries within a constrained quad so they don't read as mechanically straight) — real technique, but it's cosmetic stylization, not a fix for the mesh-resolution-driven coastline/overlay mismatch already tracked elsewhere in this doc; revisit for visual polish once the M4 rendering milestones land, not before. *Moisture fed by rivers/lakes* (the article's "distance to fresh water" includes rivers) — ours only seeds from `!isLand` cells; adding rivers as a moisture source creates a pipeline-ordering problem since moisture is computed *before* rivers (river sourcing reads moisture), so it needs a two-pass moisture computation — bigger change, not done here.
- **M1.1 — Ridge-line mountain shaping, decoupled from planet/cell scale — done (2026-08-27)**: prompted by Bruno observing that mountains formed as a blob clumped at continent centers instead of a line, and that shrinking the planet made whole continents turn mountainous. Root cause (confirmed by reading `elevation.ts`/`plate-boundaries.ts`): `computeElevation()`'s `spreadInfluence()` pushed every boundary edge's uplift outward `boundaryFalloffRadius` (3) graph-hops, decaying per hop — and a mountain *range* is many adjacent convergent edges in a row, each spreading independently, so their overlap compounded into a blob covering most of a continent's interior. Being hop-count-based (not physically scaled), the blob's footprint relative to a whole landmass grows as cell count/planet size shrinks — exactly the scale-dependence Bruno was seeing. Separately, `computeBiomes()`'s `'alpine'` classification rode a global elevation-percentile threshold on that same smoothed field, so the *visual mountain* and the *actual tectonic ridge* (already available as `ridgeCellIds`, unused for this) were only coincidentally related.
  - **Fix**: continent-continent convergent (ridge) *and* ocean-ocean convergent (island-arc — the same real-world phenomenon, a line of collision uplift, just underwater) edges now use a new `ridgeFalloffRadius` param (default 0 — no spread past the boundary's own two cells) instead of the general `boundaryFalloffRadius`. Subduction and rift/mid-ocean-ridge contributions are untouched (those are realistically broad regional features, e.g. the Andes' uplift belt, not a single line). `computeBiomes()` now takes `ridgeCellIds` and classifies them `'alpine'` unconditionally (still gated behind the existing frozen/land checks), on top of — not replacing — the elevation-percentile check, so ridge cells always read as a mountain line tracing the actual boundary geometry regardless of cell density or planet size, while other compounded-tall terrain (e.g. a subduction zone) can still qualify via the percentile path.
  - **Follow-on fix, same day**: with ridge/island-arc spread removed, `landRelief` (max land elevation minus sea level) dropped to its realistic un-inflated scale — it turned out several other biome tests were implicitly relying on the old inflated scale. `computeBiomes()`'s `flatnessSlopeFraction` default (meadow-vs-hills cutoff) was recalibrated from 0.08 to 0.2 after empirically sampling the actual normalizedSlope distribution across seeds (old default was stricter than the *minimum* slope in the new data — meadow cells had become impossible to produce at all). Two hardcoded test seeds (`biomes.spec.ts`'s meadow/desert tests) were swapped for seeds verified (via a throwaway `tsx` sweep script, not committed) to still produce that biome under the corrected model — not a workaround, since the land/water *pattern* legitimately shifts with different elevation shaping even at the same `targetLandFraction`.
  - **Follow-on fix (2026-08-28) — coastal deserts were structurally impossible**: a `biomes.spec.ts` test asserted "deserts never touch the coast" as an invariant — Bruno correctly called this out as backwards (Atacama, Namib, Baja California, Australia's west coast are all real coastal deserts) and pointed out that deleting the test doesn't fix the actual generation bug it had encoded. Root cause: `climate.ts`'s moisture was a pure BFS distance-from-ocean field, so a coastal land cell (always 1 hop from an ocean source) was structurally guaranteed to be well above the dry-moisture threshold — deserts could *only* form far enough inland to exhaust that field, regardless of any other condition. Fixed by adding a second, independent dryness term: `aridBeltCenter`/`aridBeltWidth`/`aridBeltStrength` model Earth's subtropical high-pressure belts (~20-30° latitude both hemispheres, Hadley-cell descent suppressing rainfall independent of distance from water) as a triangular multiplier over `|y|` applied to land moisture after the distance field. This is the same real phenomenon that drives Bruno's actual coastal-desert examples, and it composes with the existing field rather than replacing it — inland deserts (dry via distance) still form same as before. Verified empirically: 79/80 swept seeds now produce at least one coastal desert cell, while still producing plenty of interior ones. The old (wrong) invariant test was removed and replaced with `biomes.spec.ts`'s "deserts can be coastal, not just interior" test, which positively asserts at least one coastal desert exists at a fixed seed rather than asserting the old absence.
  - **Considered, not done — the rest of desert/rainfall sophistication (Bruno's #1 ask)**: the arid-belt fix above only addresses "deserts were structurally confined to continent interiors" — it's still an isotropic, static, one-shot field, not the fuller ask. Proposed direction for the rest: a latitude-banded prevailing-wind model (3-cell atmospheric circulation — trade winds/westerlies/polar easterlies, a known cheap pattern) walking moisture downwind instead of isotropically, depleting extra moisture crossing a ridge cell (true orographic rain-shadow, distinct from the arid belt's latitude-only effect). For the "dynamic weather / desertification as a consequence of play" half of the ask: that implies moisture becoming a live, mutable field (not a one-shot generation output) — worth designing this pass so a later runtime layer can perturb it (similar shape to the sparse terrain-edit override layer planned for M4e), but actually simulating weather live is a separate, bigger feature, not scoped here.
  - **Considered, not done — volcanoes (Bruno's #4 ask)**: cheap once ridge-line data exists, since the boundary types are already classified — ocean-continent subduction (continental-side uplift, real-world analog: Andes/Cascades volcanic arcs), ocean-ocean convergence (island arcs, now already treated as a sharp line above), and oceanic divergence (mid-ocean ridges) are all classic volcanism sites. A sparse `volcanoCellIds` (same shape as `ridgeCellIds`) tagging a subset of those boundary cells is the natural next step — not done this pass.

  - **M4b — Chunking — done (2026-08-28)**: `chunking.ts` (`buildPlanetChunks()`, `buildChunkMeshData()`) in `worldgen/core`.   - **M4c — Per-chunk discrete LOD — done (2026-08-28)**: 2 fixed levels per chunk (the milestone's "2–4" range, deliberately starting at the low end — see below), added to `chunking.ts`. LOD0 is the existing `buildChunkMeshData()` (full per-cell detail). LOD1 is new: `buildChunkBoundaryLoop()` walks a chunk's outer edge (an edge `corners[k]→corners[k+1]` of a member cell is a boundary edge iff the cell across it, per `IPlanetGraphCell`'s neighbor/corner indexing, belongs to a different chunk) and chains boundary edges head-to-tail by object identity into a closed loop — cheap and exact because corner positions are shared object references between every cell touching that Voronoi vertex (`dual-cells.ts`), not recomputed per cell. `buildChunkLod1MeshData()` applies that loop extraction not to the chunk as a whole but to **merge groups within it** — contiguous cell clusters grown by the same BFS (`growConnectedGroups()`, now shared with `buildPlanetChunks()`) under a curvature-error budget — and renders each group as one flat polygon over its merged boundary. The key property: a merged polygon's vertices are the *exact same* corner objects a neighboring chunk's LOD0 cells use along that shared border, and their elevations (`cellCornerElevation()`) are mathematically the same `(a+b+c)/3` regardless of which of the 3 surrounding cells computes them — so LOD0-to-LOD1 borders never crack, with no skirt or explicit stitching pass, in either direction, for any neighbor-LOD combination. (Elevations agree to floating-point summation-order rounding, ~1e-16 for typical magnitudes — far below float32 precision, confirmed by a dedicated unit test.) Falls back to full-resolution for any group whose boundary isn't a single simple loop — including a group that owns the entire graph (nothing to seam against), and, since a second same-day fix, any ring-shaped or pinched region, which `buildChunkBoundaryLoop()` now detects by checking that the traced loop consumed every boundary edge (`positions.length === nextByStart.size`) rather than assuming it did and silently emitting a truncated loop.
    - **Same-day bug + fix (1 of 2 — triangulation)**: the first version fanned the boundary loop from a single interior point (the chunk's own centroid) instead of triangulating it properly. A single-point fan only tessellates a polygon correctly when the polygon is *star-shaped* around that point (every boundary point visible from it without crossing an edge) — BFS-grown chunk regions are frequently non-convex "amoeba" shapes (flood-fill has no compactness heuristic), so the centroid routinely wasn't star-shaped-safe, and the fan triangles folded over each other. Visually this looked like sharp radiating spike/pinwheel patterns replacing recognizable terrain at LOD1 (caught by Bruno from a screenshot: "the far ones are unrecognizable... perhaps the geometry is all at the same point"). Fixed by replacing the fan with a real ear-clipping polygon triangulation (`triangulatePolygon2D()`, new in `chunking.ts`) run on the loop projected into a local tangent-plane 2D basis at the chunk's centroid — the projection only decides *which* vertex triples form triangles, output positions/elevations are still the real 3D loop data. Ear clipping has no star-shaped requirement (works for any simple polygon, convex or concave) and needs no interior apex vertex at all, so LOD1 triangle count actually dropped from `boundaryVertexCount` to `boundaryVertexCount - 2`. Locked in with a dedicated test: a concave "L"-shaped polygon (reflex vertex right where a centroid-fan would have broken) triangulated into exactly `n-2` triangles whose summed area exactly matches the polygon's own shoelace area — the check that would have caught the original bug (overlapping fan triangles make that sum diverge from the true area).
    - **Same-day bug + fix (2 of 2 — the actual one)**: the ear-clipping fix above was a real fix to a real bug, but it was not the bug in the screenshot; Bruno re-tested and reported "not much improvement, same looking issue." The genuine defect was never topological — it was that collapsing an entire chunk to a single flat polygon is the wrong LOD, for a reason that renders as garbage rather than as an obviously-too-coarse mesh. **A flat polygon spanning a spherical cap of angular radius `r` sags below the sphere by `1 - cos(r)` at its center.** At this module's chunk sizes (a few tens of chunks per planet, so `r` ≈ 20–35°) that's 0.06–0.18 of planet radius — one to two orders of magnitude past the *entire* terrain relief being rendered (~0.02 at the lab's default elevation scale). Each chunk stopped being a coarse surface and became a chord plate buried inside the planet, so land sank beneath the fixed-radius sea-level shell and the ocean rendered in front of the continents, with the plate's triangles fanning out through it — which is exactly what the screenshot showed. It also explains why the ear-clipping fix changed nothing visible: ear clipping on a near-convex loop *legitimately* produces fan-like radiating triangles, so the corrected triangulation looked identical to the broken one. **Fix**: LOD1 now merges cells into small groups bounded by that sag (`IChunkLod1Params.maxSag`, default 0.002 → cap radius ~3.6°, applied to candidate cells' corners during BFS growth) instead of collapsing the whole chunk. A cell-*count* cap was tried first and rejected by measurement: BFS groups aren't discs (later groups fill the stringy gaps between earlier ones), so an 8-cell cap still measured 0.073 max sag — a stringy 8-cell group spans roughly twice the angle of an 8-cell blob. Bounding the sag directly took it to 0.0067, whose remaining floor is just a single large cell polygon's own curvature. Consequence worth stating plainly: the payoff now scales with resolution rather than being constant. At the lab's default 180 cells one cell already exceeds the budget, so groups bottom out at one cell and LOD1 degenerates to "cell polygons minus their fan centers" (`n-2` triangles per cell instead of `n`, ~⅓ saving); the merge only starts compounding at the high end of the cell-count slider. That is the correct behavior for a geometric-error-budget LOD — it saves more where there is more to save — but it does mean LOD1 is nearly free of benefit at low cell counts, which the previous (broken) version disguised by simply throwing the geometry away.
    - 10/10 new unit tests passing (`chunking.spec.ts`, boundary loop + LOD1 + triangulation): boundary loop closes with ≥3 vertices, every boundary vertex is bit-identical in position (and numerically identical in elevation) to the corresponding corner on whichever neighboring chunk's cell also touches it, `null` when the region owns the whole graph, LOD1 has strictly fewer vertices than LOD0 for a typical chunk, LOD1 vertices sit on the unit sphere, the unbounded-merge fallback matches LOD0 exactly, the two `triangulatePolygon2D()` tests above, and — the regression test for bug 2 — **max sag across every LOD1 triangle stays within `worstSingleCellSag + maxSag` and under a tenth of what the same chunk collapsed whole would produce**, with both bounds derived from the graph and the documented budget rather than tuned to observed numbers. 72/72 tests passing total.
    - **Follow-up (2026-08-28) — feature pinning, so the merge itself stops popping**: even with sag bounded, Bruno reported a live version of the geomorphing problem: switching a chunk from LOD0 to LOD1 could flatten an interior mountain to its surrounding color, make a small island disappear (fully absorbed into a merge group dominated by its water/land neighbors), or shift the rendered coastline, since LOD1 only keeps a merge group's *boundary* vertices — anything interior to a group, however distinctive, is simply gone. A hard "pin everything above a prominence/size threshold" was considered and rejected before writing any code: it regresses exactly where LOD1 matters most, since a genuinely mountainous chunk has most of its cells clear a fixed bar, so LOD1 would do nothing right where the triangle count is highest. Landed instead as `salience.ts` (`computeCellPins()`) — a **per-chunk top-K budget**, not a threshold, ranking three independent categories and pinning only the winners to always render as their own single-cell polygon at both LODs: peaks by *prominence* (elevation minus neighbor average, so a uniformly tall plateau doesn't all qualify — only what genuinely sticks out from its immediate surroundings does), coastline features by curvature (each `extractCoastlines()` loop vertex compared against the midpoint of neighbors a few steps along the same loop — a straight shoreline scores near zero, a cape or bay mouth scores high), and islands (land flood-filled into connected components, the single largest excluded as "mainland", the rest ranked by cell count and pinned **whole or not at all** — partially pinning an island would still show its unpinned half flattening, the exact popping this exists to prevent). `growConnectedGroups()` (shared by `buildPlanetChunks()` and LOD1's merge) takes an optional `pinned: Uint8Array`: a pinned cell is skipped as a candidate neighbor by every other group and never expands its own frontier if it becomes a seed, so it's always a singleton group — `buildPlanetChunks()` passes nothing and is unaffected (pinning is LOD1-only). Computed once per graph in `/cell-planet-lab`'s `rebuildPreviewMesh()` (not per chunk, not per frame) and threaded into every chunk's `buildChunkLod1MeshData()` call as `{ pinned }`. 6 new unit tests (2 in `chunking.spec.ts` for the `growConnectedGroups()` pinning mechanic itself, 4 in the new `salience.spec.ts` for `computeCellPins()`'s peak/budget/island-ordering/mainland-exclusion behavior), 78/78 tests passing total.

## World profiles + per-cell terrain features (spike, 2026-08-29)

Bruno's ask, ahead of M5: a civilisation-game feel at large scale, where a single cell can *be*
a discrete landform (a whole mesa, volcano, crater) rather than only an emergent blend of many
cooperating cells' tectonic elevation; other world types (starting Moon-like); and — his own
addition — lava lakes and lava rivers "for some planets," including a planet-scale molten ocean
on a young/hot world, not just a puddle by a volcano. Explicitly scoped as a spike: prove the
direction, not a finished system.

- **`IWorldProfile`** (`worldgen/core/world-profile.ts`): named bundles (`terran`/`moon`/
  `volcanic`/`protoplanet`) of overrides across the *existing* tectonics/climate/biome param
  bags plus the new feature params and an `oceanSubstance: 'water' | 'lava'` flag — not a new
  pipeline. `terran` is an intentional no-op. `climate.ts` gained one real addition,
  `baseTemperatureOffset`, so `moon` reads as cold/airless, not just dry.
- **`computeFeatures()`** (`worldgen/core/features.ts`): per-cell `Feature` typing
  (volcano/mesa/crater/lava_lake) plus real shape stamps, reusing **`geological-features-lab`'s
  analytic height functions** (relocated verbatim, framework-free, into
  `worldgen/core/geological-shapes.ts` — cone+rim+crater+erosion, bowl+rim+ejecta,
  cap+talus+edge, far better than a from-scratch flatten/dig) instead of reinventing landform
  shapes. A feature's footprint is `cellsWithinHops()` (reused from `terrain-edits.ts`) around a
  seeded-candidate site cell; each footprint cell's own elevation is resampled through the
  matching geological function, projected onto a local tangent plane (the same gnomonic
  construction `buildColliderPatch()` uses), and the result materializes into a fresh per-cell
  array via `buildFeatureElevation()` — same "copy once, overwrite touched indices" shape as
  M4e's `buildEffectiveElevation()`, composed the same way (features first, player edits win on
  top). No changes needed to `chunking.ts`/`collider-patch.ts`/`sample-elevation.ts` at all: none
  of them call `sampleElevation()` internally, they just read whichever `elevation[]` array
  they're handed, which is exactly the property the M4e edit layer already depended on.
- **Lava is two different mechanisms, not one** — Bruno's correction mid-spike, since the first
  draft only modeled a small volcano-adjacent puddle: (1) `Feature: 'lava_lake'` tags an existing
  `waterBodyKind === 'lake'` cell near a volcano instance — local, small, coexists with an
  ordinary water ocean elsewhere. (2) `WorldProfile.oceanSubstance: 'lava'` (the `protoplanet`
  preset) substance-flags the *entire* largest `classifyWaterBodies()` component unconditionally
  — no volcano-adjacency check, and every `traceRivers()` path already drains into it by
  construction, so all rivers on that profile are lava rivers for free, no separate
  source-selection logic needed.
- **River rendering upgraded from a flat debug line to a flowing ribbon** — relocated
  `river-lab`'s POC (`river-lab/river-system.ts`, a *different* problem from
  `rivers.ts::traceRivers()`: that file assumes a path already exists and handles width/flow
  interpolation + the actual ribbon mesh/shader, `traceRivers()` decides where the path runs) into
  `worldgen/render/flow-path.ts`. Its flat-plane ribbon math doesn't carry over as-is to a sphere
  (the perpendicular/width construction assumed a fixed world-up axis), so `cell-planet-lab`
  builds its own spherical ribbon geometry per river path (`perpendicular = cross(radial,
  tangent)`) but reuses the relocated file's shader materials unchanged (`createWaterFlowMaterial()`
  / new `createLavaFlowMaterial()`) since those are UV-based and geometry-agnostic. Width comes
  from `sqrt(riverFlow)` — `rivers.ts`'s own doc comment already named this as the intended use of
  that field.
- **Crater scale**: only small/mid craters this spike (`sampleCrater()`'s flat-tangent-plane
  approximation holds up to a few percent of planet radius). Giant multi-ring impact basins
  (lunar-mare scale — real maria are later lava-flooded basins, a natural but separate tie-in to
  the lava work above) would need a true angular-distance formula or generation closer to
  tectonics' own multi-hop boundary spreading; not attempted here.
- **Lab wiring**: `/cell-planet-lab` gained a world-profile button group (mirroring the
  world-size-tier picker), a `'feature'` 2D/3D map mode, a per-feature-type count stat, and the
  ribbon river/lava rendering above.
- **Non-goals for this spike**: no mesh-level vertical cliff faces for mesas (corner-blend skirt
  only); no lava heat/damage gameplay; no new `Biome` values (features layer on top of, don't
  replace, climate biomes); no dedup of the new spherical ribbon builder against
  `flow-path.ts`'s flat one.
- Verification: `ng build triangular-engine --configuration development` and
  `ng build demo-app --configuration development` both clean. Bruno's own in-browser check
  (standing practice for this lab) is the remaining step — pick each profile and confirm visual
  distinctness, toggle `'feature'` map mode and confirm feature cells are visibly *shaped*
  differently (raised rims, flat mesa tops), not just recolored.
